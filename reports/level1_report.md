# Level 1 — PV-Group Detection + Grouped Day-Ahead Forecasting

Executed from `prompts/level1_proloaf_prompt.md`. Code lives under `src/`; all
numeric artifacts referenced below (`reports/*.csv`, `reports/*.json`) are
regenerated by running:

```bash
uv sync && source .venv/bin/activate   # installs from the committed uv.lock
git submodule update --init third_party/proloaf   # vendors train.py/preprocess.py/evaluate.py

python3 -m src.pv_features           # -> reports/pv_features.csv
python3 -m src.pv_detection          # -> reports/pv_detector_scores.csv, pv_detection_metrics.json
python3 -m src.aggregate             # -> reports/{pv_group,non_pv_group,all_known_group}_hourly.csv
python3 -m src.forecast              # -> reports/forecast_metrics.json, grouping_comparison.json (LightGBM)

python3 -m src.export_for_proloaf    # -> targets/<name>/{raw,preprocessing.json,config.json}, submodule symlinks
python3 third_party/proloaf/src/preprocess.py --station pv_group
python3 third_party/proloaf/src/preprocess.py --station non_pv_group
python3 third_party/proloaf/src/train.py --station pv_group
python3 third_party/proloaf/src/train.py --station non_pv_group
python3 third_party/proloaf/src/evaluate.py --station pv_group      # native ProLoaF plots -> targets/<name>/oracles/eval/
python3 third_party/proloaf/src/evaluate.py --station non_pv_group
python3 -m src.proloaf_evaluate      # -> reports/proloaf_metrics.json (kWh-scale, comparable to forecast_metrics.json)
```

(The project has moved from Poetry to `uv` entirely — see `CLAUDE.md`'s
Environment section for why, including why `pandas`/`numpy` are pinned to
unusually narrow ranges to satisfy the `proloaf` git dependency's own pins.)

## 1. Scope and deviations from the task brief

- **ProLoaF is used**, per the brief's primary instruction, as the
  `third_party/proloaf` git submodule (pinned at the `sogno-platform/proloaf`
  commit checked in via `.gitmodules`) plus the `proloaf` package
  pip-installed into `.venv`. Both the submodule add and the pip install
  pull and execute third-party code from an external repo, which this
  sandbox's auto-mode classifier flags as requiring explicit confirmation —
  both were explicitly approved before running. See §4 for how its
  `preprocess.py`/`train.py`/`evaluate.py` driver scripts were actually
  wired up against this repo's own `targets/<name>/` config folders (which
  live here, git-tracked, not inside the submodule — see §4's note on the
  symlink trick this requires).
- **LightGBM remains the first, primary model** (§4a) — it was built before
  ProLoaF was authorized, stayed as the faster/simpler point-forecast
  baseline the brief explicitly allows, and turned out to outperform ProLoaF
  at this data scale/training budget (§4c). ProLoaF (§4b) is the second,
  directly-comparable model trained on the exact same group aggregates.
- Only `kWh_received_Total` is usable from the 15-minute files: a check
  across a random sample of households found `kWh_received_HeatPump` and
  `kWh_received_Other` are blank for effectively every row (0% populated),
  despite being present in the schema. PV-pattern detection and forecasting
  both work from the net-total signal only.

## 2. PV-pattern detection (Level 1, part a)

### Features (`src/pv_features.py`)

Households have no PV-production column, only net imported `kWh_received_Total`,
so detection has to read PV ownership out of *suppression* of net midday
import. Per household, from the hourly-resampled total:

| Feature | Intuition |
|---|---|
| `ratio_summer_midday_to_night` | PV self-consumption suppresses midday (UTC 10–14) import relative to night (UTC 22–03), in summer (Apr–Sep) |
| `ratio_winter_midday_to_night` | Same ratio in winter (Nov–Feb), when PV output is minimal — control condition |
| `seasonal_contrast` | summer ratio ÷ winter ratio — isolates the *PV-driven* seasonal effect from heat-pump-driven seasonal effects that hit both groups |
| `summer_midday_cv` | day-to-day coefficient of variation of summer midday import — PV households vary with cloud cover, heat-pump-only households don't |
| `summer_midday_zero_frac` | fraction of summer midday hours with near-zero (<0.05 kWh) net import — PV households frequently cover their own midday load entirely |
| `corr_summer_midday_vs_sunshine` | correlation of summer midday import with the nearest station's `Sunshine_duration_hourly` (only available for 5/8 stations, covering 380/410 households) |

UTC 10–14 is used as a fixed midday proxy for all households (Germany is
UTC+1/+2) rather than per-household local time, since solar generation peaks
broadly enough across that window regardless of the one-hour CET/CEST shift.

### Validation against the surveyed flag

245/410 households have a known `Installation_HasPVSystem` (131 PV, 114
no-PV); 165 are unsurveyed (blank, not coerced to `False`). A
`HistGradientBoostingClassifier` (handles the occasional missing
`corr_..._sunshine` natively) was evaluated with 5-fold **out-of-fold**
stratified cross-validation, so every household is scored by a model that
never saw it:

| Metric | Value |
|---|---|
| ROC AUC | **0.937** |
| Accuracy | 0.894 |
| PV precision / recall / F1 | 0.913 / 0.885 / 0.899 |
| No-PV precision / recall / F1 | 0.873 / 0.904 / 0.888 |

Confusion matrix (rows = true, cols = predicted; order no-PV, PV):

```
[[103  11]
 [ 15 116]]
```

`summer_midday_zero_frac` dominates permutation importance (0.301; all other
features combined ≈ 0.041) — a near-zero summer midday import is by far the
strongest tell. The detector was then fit on all 245 labelled households and
applied to the 165 unsurveyed ones: **27 flagged as likely PV, 138 as
likely no-PV** (`reports/pv_detector_scores.csv`, column
`detector_pred_pv`). These detector-based labels were **not** used to define
the forecasting groups below (per the brief, the surveyed flag is the
grouping key, the detector is a validation exercise); the secondary
detector-based-grouping forecast comparison was skipped for time.

## 3. Grouped hourly aggregation (`src/aggregate.py`)

Groups are defined directly from the surveyed flag: **131 PV households**,
**114 no-PV households** (165 unsurveyed households excluded from both).

**Partial coverage.** Households were instrumented at different times across
2019–2024 (per-household coverage varies, see
`data/smart_meter_meta_data/smart_meter_data_15min_overview.csv`), so a group's
active-household count ramps up over the raw series. Summing blindly over the
full history would make the aggregate's level track meter rollout rather than
demand. Each group's series is restricted to the trailing window where at
least 70% of its eventual household count is reporting, and the active count
is kept as a column:

| Group | Households | Stable window | Active count (mean / min / max) |
|---|---|---|---|
| PV | 131 | 2022-12-01 → 2024-02-27 (10,896 h) | 115.4 / 0 / 127 |
| No-PV | 114 | 2022-04-14 → 2024-02-27 (16,440 h) | 96.4 / 0 / 109 |

Even inside the stable window, one full calendar day (**2023-10-29**, all
households in the PV group simultaneously) is a 0-coverage gap — an
apparent provider-side outage, not a bug in the aggregation; it's left as
`NaN` and dropped downstream rather than imputed. 120 (PV) / 72 (no-PV) hours
total fall below the 70% threshold inside the stable window and are flagged
in `below_coverage_threshold` but not dropped, since they're scattered single
missing meters rather than wholesale gaps.

**Multi-station weather.** Each group's households map to multiple weather
stations (e.g. PV group: 52 households on station `Hg`, 52 on `8jB`, the rest
split over 6 smaller stations). Group-level weather is a
household-count-weighted average across the stations actually used by that
group, renormalised per-timestamp over whichever stations have that variable
populated (`Sunshine_duration_hourly` only exists for 5/8 stations).

## 4a. Day-ahead forecasting — LightGBM (`src/forecast.py`)

**Target & resolution:** hourly-summed `kWh_received_Total` per group
(justification: aligns with the hourly weather data without discarding the
sub-hourly structure needed to model midday PV suppression, and matches
ProLoaF's typical granularity had it been used).

**Forecast definition:** a forecast is issued at `origin` = midnight UTC of
day D+1, using only day-D-and-earlier data, predicting all 24 hours of day
D+1 (horizon `h` = 0..23).

**No-leakage lag design:** only lags ≥24h are used (`lag_24`, `lag_48`,
`lag_168`, plus a 24h rolling mean spanning `t-48h..t-24h` and a 7-day
same-hour rolling mean). This isn't an arbitrary cutoff — for horizon `h>0`,
target time `t = origin + h`, so any lag `L` is guaranteed to land at or
before `origin-1` (still known at forecast time) only when `L ≥ 24`; a naive
"previous hour" feature, for instance, would be safe for `h=0` but leak
future same-day information for every `h>0`.

**Known simplification (weather):** there is no day-ahead weather *forecast*
in this dataset, so same-day weather **actuals** at the target timestamp are
used as a stand-in, as explicitly sanctioned by the brief. This inflates
reported accuracy versus a deployment using real forecasts and is the single
biggest external-validity caveat on the numbers below.

**Split:** chronological by whole origin-day, 80% train / 20% test (never
split within a day).

**Model:** single `LGBMRegressor` per group trained across all 24 horizons
jointly (horizon is itself a feature), rather than 24 separate per-horizon
models — simpler, and `hour`/`horizon` dominate feature importance anyway so
the pooled model learns horizon-specific behaviour fine.

### Results

| Group | Households | Test period | MAE (kWh/h) | RMSE | MAPE | MAE/household | Naive (same hour, last week) MAE |
|---|---|---|---|---|---|---|---|
| PV | 131 | 2023-12-01 → 2024-02-27 | 32.31 | 39.44 | **15.9%** | 0.247 | 53.88 |
| No-PV | 114 | 2023-10-13 → 2024-02-27 | 14.87 | 18.59 | **8.4%** | 0.130 | 37.19 |
| All-known (ungrouped) | 245 | 2023-11-27 → 2024-02-27 | 45.06 | 55.27 | 10.8% | 0.184 | 92.49 |

Both grouped models beat the naive "same hour, same weekday, last week"
baseline by roughly 1.7–2.5x on MAE, so the LightGBM models are learning real
structure, not just leaning on calendar regularity.

Top features by gain, both groups: `hour`, `rolling_mean_24_48`,
`Temperature_avg_hourly`, `lag_24` — i.e. time-of-day, recent history, and
temperature dominate, with sunshine/precipitation/wind well behind (full
tables in `reports/forecast_metrics.json`).

### Did grouping actually help?

The three rows above aren't directly comparable — each model's test window
is "that series' own last 20% of days," and the series have different stable
windows. Re-scoring all three on the **same** common test window (from
2023-12-01, the latest of the three start dates) for a fair comparison
(`reports/grouping_comparison.json`):

| Approach | MAE/household | MAPE |
|---|---|---|
| Single ungrouped model (all 245 households) | **0.1850** | 10.8% |
| Grouped (PV model + no-PV model, summed) | 0.1898 | PV 15.9% / No-PV 7.3% |

**Honest finding:** on raw per-household MAE, grouping is a wash — slightly
*worse* than a single pooled model (0.190 vs 0.185 kWh/h/household). This is
expected: summing 245 households into one series averages out more
idiosyncratic noise than summing 131 or 114, so the pooled series is
statistically "smoother" and easier to hit on absolute error alone.

Where grouping clearly does pay off is **relative accuracy and risk
characterisation**: the pooled model's 10.8% MAPE hides that the PV segment
is forecast far less reliably (15.9% MAPE) than the no-PV segment (7.3%
MAPE). For day-ahead procurement, that gap matters more than the pooled
headline number — it tells E.ON exactly where forecast risk concentrates
(the PV-owning segment, driven by weather-dependent self-consumption) and
where a wider safety margin / more conservative procurement buffer is
warranted, which Level 3's uncertainty framing would act on directly. A
single ungrouped model would never surface that.

## 4b. Day-ahead forecasting — ProLoaF (`third_party/proloaf` + `src/export_for_proloaf.py`, `src/proloaf_evaluate.py`)

**Wiring ProLoaF's scripts up to this repo.** `preprocess.py`/`train.py`/
`evaluate.py` all resolve `targets/<station>/...` relative to the
submodule's own root (`dirname(dirname(__file__))` inside `third_party/proloaf/src/`),
not the caller's cwd — and `preprocess.py` specifically has no `--config`
override to point elsewhere (`train.py`/`evaluate.py` do). Rather than
duplicating `targets/<name>/` inside the submodule (which would make it
untracked by this repo, since content placed inside a submodule's working
tree belongs to *its* git history, not the superproject's), `targets/<name>/`
lives at this repo's root as the single tracked source of truth, and
`src/export_for_proloaf.py` maintains a symlink
`third_party/proloaf/targets/<name>` → `../../../targets/<name>/` so the
scripts find it. (Rerun `python3 -m src.export_for_proloaf` to recreate the
symlinks after a fresh `git submodule update --init`, since symlinks inside
a submodule's tree aren't preserved across clones either.) Every path inside
`targets/<name>/preprocessing.json`/`config.json` (`data_path`,
`output_path`, `log_path`, `evaluation_path`) is accordingly written relative
to the submodule root as `../../targets/<name>/...`, so all of ProLoaF's
generated data/models/logs/eval-plots land back inside `targets/<name>/`
here, not inside the submodule.

**Preprocessing.** `src/export_for_proloaf.py` takes the *same*
`reports/<name>_hourly.csv` group aggregates §3 built (so both models are
trained on identical input data), strips the `+00:00` UTC-offset suffix
ProLoaF's fixed-format CSV parser (`"%Y-%m-%d %H:%M:%S"`, no `%z`) can't
parse, and writes `targets/<name>/raw/<name>_raw.csv`. ProLoaF's own
`preprocess.py` is then run **unmodified** against that file: it resamples
to a continuous hourly index (`set_to_hours`), seasonally interpolates gaps
via `fill_if_missing`/`custom_interpolate` — including the full 2023-10-29
outage day from §3, filled using ±24h/48h/... neighbours plus a trend
correction, rather than the LightGBM pipeline's drop-the-row approach, since
an RNN needs an unbroken sequence — and adds cyclical (`hour_sin/cos`,
`weekday_sin/cos`, `mnth_sin/cos`) and one-hot time features, writing
`targets/<name>/data/<name>.csv`.

**Model config** (`targets/<name>/config.json`): `history_horizon=168` (1
week, matching the LightGBM `lag_168` feature), `forecast_horizon=24`,
`frequency=1h`, recurrent (LSTM) encoder-decoder, default `NllGauss`
(Gaussian negative-log-likelihood) loss — i.e. ProLoaF predicts a full
distribution per hour, not just a point estimate. `encoder_features` =
target + all 6 weather columns (full history); `decoder_features` = the 6
weather columns only (same simplification as LightGBM: same-day weather
**actuals** stand in for an unavailable day-ahead forecast, carried through
here too). `train_split=0.6` / `validation_split=0.8`, so `evaluate.py`'s
test set is the same last-20%-chronological convention as the LightGBM
pipeline. Both groups converge and early-stop (patience 7) well inside the
`max_epochs=40` budget — 13–22 epochs, ~30–45s each on CPU.

**Evaluation protocol.** ProLoaF's own `evaluate.py` is run unmodified first
(native output under `targets/<name>/oracles/eval/`: metrics plots, two
sample-window forecast plots), but its benchmark metrics are computed in
*scaled* `[0,1]` space and only two sample windows are plotted, not scored
end-to-end — not usable for a head-to-head kWh comparison with the LightGBM
table. `src/proloaf_evaluate.py` instead: runs every sliding window of the
held-out test set through the trained model in one batched forward pass,
keeps only the windows whose first forecast hour is local midnight (so each
kept sample is a genuine "forecast issued at midnight for the next 24h",
matching the LightGBM pipeline's `origin` definition instead of ProLoaF's
default one-sample-per-hour sliding window), and inverse-transforms
predictions back to kWh via each model's own fitted per-column
`MinMaxScaler` before computing MAE/RMSE/MAPE. It also reports PICP
(prediction-interval coverage) at ProLoaF's default 95% nominal level — one
metric that needs no unit conversion, and a concrete example of the
uncertainty quantification a point-forecast model like LightGBM doesn't
provide natively.

### Results (ProLoaF)

| Group | Households | Day-ahead test windows | Test period | MAE (kWh/h) | RMSE | MAPE | MAE/household | PICP (95% nominal) |
|---|---|---|---|---|---|---|---|---|
| PV | 131 | 83 | 2023-12-07 → 2024-02-27 | 36.86 | 45.91 | 19.2% | 0.281 | 88.4% |
| No-PV | 114 | 130 | 2023-10-21 → 2024-02-27 | 22.26 | 27.52 | 12.1% | 0.195 | 93.6% |

(Test windows are fewer and start slightly later than the LightGBM table's:
`history_horizon=168h` has to be consumed from the front of ProLoaF's own
`validation_split`-defined test slice before the first forecastable origin,
and only midnight-aligned origins are kept per the protocol above — both
models are still evaluated on the same underlying last-20% period, just with
a different count of eligible origins within it.) Full per-window
predictions: `reports/{pv_group,non_pv_group}_proloaf_test_predictions.csv`;
summary: `reports/proloaf_metrics.json`.

PICP is close to but under the 95% nominal target for the PV group (88.4%)
and over it for the no-PV group (93.6% — reasonably close) — on this little
data (83 and 130 test windows respectively) that's within plausible noise
for a calibration check, not strong evidence of systematic miscalibration
either way, but it's exactly the kind of check Level 3 (uncertainty) would
want to do with more test data before trusting the intervals operationally.

## 4c. LightGBM vs ProLoaF

| Group | Model | MAE (kWh/h) | RMSE | MAPE | MAE/household |
|---|---|---|---|---|---|
| PV | LightGBM | **32.31** | **39.44** | **15.9%** | **0.247** |
| PV | ProLoaF | 36.86 | 45.91 | 19.2% | 0.281 |
| No-PV | LightGBM | **14.87** | **18.59** | **8.4%** | **0.130** |
| No-PV | ProLoaF | 22.26 | 27.52 | 12.1% | 0.195 |

**Honest finding:** LightGBM beats ProLoaF on every point-accuracy metric for
both groups at this data scale and training budget. This isn't a surprise
and isn't a knock on ProLoaF's approach — an LSTM encoder-decoder typically
needs substantially more data, training time, and hyperparameter search than
gradient boosting to reach parity, none of which a one-day hackathon's
~9,000–16,000 hourly training rows and a single untuned 40-epoch run provide
(no `exploration`/Optuna tuning pass was run; `targets/<name>/config.json`'s
`exploration` flag and `tuning.json` convention are there for that if more
time were available). What ProLoaF provides that LightGBM's plain point
forecast doesn't is **native uncertainty quantification** (the PICP numbers
above come for free from the `NllGauss` loss, no extra modelling work) —
directly the kind of signal Level 3's "where is the model more/less certain"
framing would consume, and worth the accuracy gap for that reason alone in a
context where over/under-procurement costs are asymmetric.

## 5. Summary of simplifications / honesty notes

- Both LightGBM (§4a) and ProLoaF (§4b) are trained on the *identical* group
  aggregates from §3, so §4c's comparison isn't confounded by different
  input data — only by model family, training budget, and (for ProLoaF) the
  exact test-window count (§4b's note on history-horizon consumption).
- Forecasting groups use the *surveyed* PV flag, not the detector's labels;
  165 unsurveyed households are excluded from both forecasting groups
  entirely (not split into a third "unknown" group).
- Weather is same-day **actuals** standing in for an unavailable day-ahead
  forecast — reported accuracy is optimistic relative to real deployment, for
  both models.
- UTC 10–14 is used as a fixed "midday" proxy for all households rather than
  adjusting per household for CET/CEST — a one-hour approximation.
- No Level 0 baseline existed elsewhere in the repo to compare against; the
  "all-known ungrouped" model built here serves as that baseline instead.
- One full-day, group-wide data gap (2023-10-29) was found; LightGBM's
  pipeline drops the resulting NaN rows, ProLoaF's `fill_if_missing` instead
  seasonally interpolates it (§4b) — a deliberate difference, not an
  inconsistency, since an RNN needs an unbroken sequence and gradient
  boosting's per-row features don't.
- ProLoaF's hyperparameters (epochs, batch size, learning rate, LSTM size)
  were set once from the `targets/opsd` reference example's ballpark and not
  tuned — §4c's gap is partly a training-budget artifact, not necessarily a
  ceiling on what ProLoaF could do on this data.
